# Message 会话置顶快速参考

## 研究目标

确认移动端消息列表中“置顶会话”的常见入口、排序和视觉反馈，为 TopTop Message 的侧滑置顶方案提供模式依据。

## 参考模式

### 模式 A：会话列表内直接管理

用户在消息列表直接对目标会话执行手势，再点击明确动作。价值是无需先进入聊天设置，适合高频整理任务。

- 用户指定参考：微信式会话列表管理。
- 可迁移点：操作发生在会话列表原位；动作完成后会话立即移动到置顶区域；已置顶项提供可见区别。
- 上下文差异：公开资料对微信不同版本的手势方向和动作入口描述不一致，有左滑“更多”、右滑“置顶”、长按菜单或进入聊天设置等多种说法。因此本方案只采用“列表内侧滑后出现明确置顶动作”的通用模式，并以用户明确要求的左滑作为 TopTop 交互合同，不声称与某一微信版本逐像素一致。

参考：

- WeChat 2026 功能介绍：进入聊天信息后开启 `Sticky on Top`；强调置顶后持续位于列表顶部。  
  https://chengdu-expat.com/wechat-hidden-features/
- 微信折叠置顶聊天介绍：置顶较多时可折叠，避免普通未读会话被遮挡；该能力仅作为规模风险参考，不自动纳入本期。  
  https://www.163.com/dy/article/JU078SK9055629UX.html
- WeCom 官方帮助：移动端可在聊天设置中开启置顶；置顶超过一屏后出现折叠入口。  
  https://open.work.weixin.qq.com/help2/pc/21681

### 模式 B：置顶状态立即可见

置顶不应只改变排序，否则用户难以区分“恰好最新”与“主动置顶”。

- 推荐采用低强调度背景区分，同时增加非颜色线索，例如置顶图标或可访问状态文本。
- 未读数、时间和消息摘要保持原有语义，不因置顶而改变。
- 取消置顶后恢复普通列表视觉，并按既定排序规则回到普通会话区。

### 模式 C：可逆动作不二次确认

置顶属于低风险、可逆整理操作。

- 点击后立即生效，不弹确认对话框。
- 侧滑动作应在执行后自动收起。
- 通过位置变化、状态视觉和辅助技术播报共同反馈结果。
- 若产品希望降低误操作，可增加轻量撤销反馈，但不应阻断主流程。

### 模式 D：置顶过多需要治理

微信与 WeCom 都提供了置顶过多后的折叠思路。这说明置顶不是无限增加后仍无成本的能力。

- 本期不默认实现折叠。
- 在 brief 中确认是否限制置顶数量。
- 若允许大量置顶，应单独设计折叠、展开、未读暴露和排序规则。

## Adopt

- 在 Message 会话行左滑后显示“置顶”；已置顶行显示“取消置顶”。
- 执行后即时重排，不弹确认。
- 置顶会话形成列表顶部的稳定分区。
- 用“轻量背景 + 非颜色状态线索”区分置顶，不只靠颜色。
- 一次只展开一个会话的侧滑操作区；垂直滚动时关闭已展开项。
- 保留未读、消息摘要、时间和进入会话行为。

## Avoid

- 只改变排序，不显示置顶状态。
- 仅使用背景色表达置顶，导致无障碍用户无法识别。
- 左滑时整行仍可误触进入会话。
- 多行同时保持展开，造成列表操作混乱。
- 未确认上限和排序规则就照搬“折叠置顶”。
- 把微信某一版本的颜色、尺寸或手势方向当作 TopTop Kit 规范。

## Needs validation

- 置顶分区内部按最新消息时间、置顶时间还是手动顺序排列。
- 新置顶会话是进入置顶区首位，还是按最新消息时间插入。
- 置顶上限，以及超过上限后的提示或折叠策略。
- 设置是否账号同步，以及离线操作失败后的回滚方式。
- 私聊、群聊、Room Group、系统通知是否全部支持置顶。
- 视觉区分采用何种现有语义 Token；当前 `regular-list` 尚无 `pinned` 状态。
